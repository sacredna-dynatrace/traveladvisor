PART 1

Agent 동작 원리 한눈에 보기

여행사 창구 직원(Agent)이 필요한 도구(Tool)를 스스로 골라 쓰며 답을 만들고, Dynatrace는 그 모든 과정을 한 건의 Trace로 기록합니다.

flowchart LR U[사용자
Web Browser] -->|여행지 요청| A[travel-advisor
FastAPI] A --> P{Pipeline} P -->|None| L1[LLM 1회 호출] P -->|RAG| R[FAISS 문서 검색] --> L2[LLM 답변] P -->|Agentic| AG[travel-advisor-agent] AG --> T1[valid_city Tool] AG --> T2[travel_advice Tool] A -. OneAgent .-> DT[Dynatrace]

None은 LLM을 한 번 호출하고, RAG는 문서를 먼저 검색한 뒤 호출합니다. Agentic은 LLM이 스스로 판단해 여러 번 호출되는 구조라서 보이지 않으면 비용과 지연을 통제할 수 없습니다.

Agent 구성 요소

Agent(pipeline/agentic.py)는 도구, 행동 규칙, 반복 실행기 세 가지로 이루어집니다.

① 도구 (Tools)

Agent가 쓸 수 있는 함수입니다. Agent는 각 함수의 설명(docstring)을 읽고 어떤 도구를 쓸지 고릅니다. 도구 안에서도 LLM이 다시 호출됩니다.

Tool역할
valid_city입력한 여행지가 실제 도시인지 확인
travel_advice여행 조언 생성
movie_quote영화 대사 (Agent가 엉뚱한 도구를 고르는지 확인하는 미끼)
python
@tool
def valid_city(city: str) -> bool:
    """Returns if the input is a valid city"""   # ← Agent가 읽는 설명
    response = get_model().chat(f"Is {city} a city? respond only with yes or no.")
    return response == "yes"

② 행동 규칙 (ReAct Prompt)

LLM에게 "생각 → 도구 선택 → 결과 확인"을 반복하고, 정해진 JSON 형식으로만 답하도록 지시합니다. 이 방식을 ReAct(Reason + Act) 패턴이라고 합니다.

text
Thought: 무엇을 할지 생각
Action: {"action": "valid_city", "action_input": {"city": "Tokyo"}}
Observation: (도구 실행 결과)
... 반복 ...
Action: {"action": "Final Answer", "action_input": "최종 답변"}

③ 반복 실행기 (AgentExecutor)

python
AgentExecutor(agent=agent, tools=tools,
              handle_parsing_errors=True,   # 형식이 틀리면 다시 시도
              max_iterations=10)            # 무한 루프 방지

④ Observability (코드 변경 없음)

Agent 코드에는 계측 코드가 없습니다. Pod에 주입된 OneAgent가 Python GenAI Langchain 기능으로 chain·Agent 실행을, provider 기능(Bedrock / Anthropic experimental)으로 LLM 호출을 자동 계측합니다.

python
def start(self, model, prompt, lang="en"):
    task = f"if {prompt} is a valid city, provide a travel advice. ..."
    response = self.agent_executor.invoke({"input": task})   # 계측 코드 없음
    return format_message(response["output"])

요청 한 건의 흐름

"도쿄"를 Agentic으로 요청하면 사용자 요청은 1건이지만 LLM은 약 5번 호출됩니다. None보다 응답이 느리고 Token 비용이 3~5배 드는 이유입니다.

sequenceDiagram participant U as 사용자 participant A as Agent participant L as Claude (LLM) participant T as Tools U->>A: 도쿄 A->>L: ① 무엇을 할까? L-->>A: valid_city 사용 A->>T: valid_city(Tokyo) T->>L: ② 도시인가? L-->>T: yes A->>L: ③ 다음 행동은? L-->>A: travel_advice 사용 A->>T: travel_advice(Tokyo) T->>L: ④ 여행 조언 생성 A->>L: ⑤ 최종 답변 정리 (한국어) A-->>U: 답변

Dynatrace에서 보이는 모습

FastAPI 요청부터 LangChain Agent 실행, 각 LLM 호출까지 OneAgent가 하나의 Trace(PurePath)로 연결합니다. 요청 한 건에 LLM이 몇 번 호출됐는지, Token을 얼마나 썼는지, 어느 단계가 느렸는지를 볼 수 있습니다.

trace (개념도)
GET /api/v1/completion                 ← FastAPI (Python FastAPI)
 └ LangChain AgentExecutor              ← Python GenAI Langchain
    ├ LLM 호출 (Agent 판단)             ← Bedrock / Anthropic sensor
    ├ Tool: valid_city → LLM 호출
    ├ LLM 호출
    ├ Tool: travel_advice → LLM 호출
    └ LLM 호출 (Final Answer)
확인 위치: Distributed Tracing에서 요청 Trace를, AI Observability → Explorer에서 LLM 요청·Token 집계를 확인합니다. 실제 Span 이름과 계층은 OneAgent 버전과 켜 둔 기능에 따라 다릅니다.
Traceloop branch(amazon-bedrock)처럼 코드에서 invoke_agent/execute_tool span을 직접 만들지 않으므로, Agents topology 표시는 OneAgent LangChain sensor가 제공하는 범위에 따릅니다.
PART 2 · DYNATRACE ONEAGENT 적용 가이드

1. 개요

애플리케이션 코드에 계측 라이브러리를 넣지 않고, Dynatrace OneAgent가 Python 프로세스에 자동 주입되어 HTTP 요청·LLM 호출·LangChain 실행을 계측합니다.

  • Dynatrace Operator: Kubernetes에 OneAgent(cloudNativeFullStack)와 ActiveGate를 배포하고, Pod가 생성될 때 OneAgent code module을 주입합니다.
  • OneAgent features: 테넌트 설정에서 켠 Python 기능(FastAPI, AWS SDK GenAI Bedrock, GenAI Langchain 등)이 AI SDK 호출을 Span으로 만듭니다.
  • Dynatrace: Grail에 저장하고 AI Observability 앱·Distributed Tracing·Davis AI로 분석합니다.
flowchart LR OP[Dynatrace Operator] -->|DynaKube| OA[OneAgent
cloudNativeFullStack] OA -->|code module 주입| A[AI 앱 Pod
Python · FastAPI] A -->|LLM 호출| B[LLM Provider
Claude · Bedrock] OA -->|Trace · Metric · Log| D[Dynatrace] D --> E[AI Observability
Distributed Tracing · Davis AI]

3. Kubernetes 배포 (Dynatrace Operator)

OneAgent가 준비된 뒤에 앱 Pod가 생성되어야 code module이 주입됩니다. 이 데모는 .devcontainer/deployment.sh가 아래 순서를 자동으로 수행합니다.

① Operator 설치

bash
helm upgrade --install dynatrace-operator oci://public.ecr.aws/dynatrace/dynatrace-operator \
  --create-namespace --namespace dynatrace --atomic

② 토큰 Secret (DynaKube와 같은 이름)

bash
kubectl -n dynatrace create secret generic kind-kind \
  --from-literal="apiToken=$DT_OPERATOR_TOKEN" \
  --from-literal="dataIngestToken=$DT_TOKEN"

③ DynaKube (dynatrace/dynakube.yaml)

yaml
apiVersion: dynatrace.com/v1beta5
kind: DynaKube
metadata:
  name: kind-kind
  namespace: dynatrace
spec:
  apiUrl: https://<tenant-id>.live.dynatrace.com/api
  metadataEnrichment:
    enabled: true
  oneAgent:
    cloudNativeFullStack: {}      # 노드 OneAgent + Pod code module 주입
  activeGate:
    capabilities: [routing, kubernetes-monitoring]
  logMonitoring: {}               # container 로그 수집

④ 앱 배포 후 주입 확인

bash
kubectl -n dynatrace get dynakube,pods
kubectl -n travel-advisor describe pod -l name=travel-advisor | grep -i dynatrace
OneAgent보다 먼저 떠 있던 Pod는 주입되지 않습니다. kubectl -n travel-advisor rollout restart deploy/travel-advisor로 다시 만들어 주세요.

6. 적용 검증

요청을 2~3번 보낸 뒤 1~2분 기다렸다가 아래 순서로 확인합니다.

  1. Infrastructure & Operations: travel-advisor Pod의 Python 프로세스가 OneAgent로 모니터링되는지
  2. Distributed Tracing: /api/v1/completion 요청 아래 LangChain·LLM 호출이 이어지는지
  3. AI Observability › Explorer: LLM 요청 수·Token 집계
  4. Notebooks(DQL): 아래 쿼리로 수치 확인

Model별 요청 수 · Token · 지연 시간

DQL
fetch spans, from: now() - 1h
| filter isNotNull(gen_ai.request.model)
| summarize requests = count(),
            input_tokens = sum(gen_ai.usage.input_tokens),
            output_tokens = sum(gen_ai.usage.output_tokens),
            p95 = percentile(duration, 95),
            by: { gen_ai.request.model }

결과가 비어 있으면 Distributed Tracing에서 LLM 호출 Span을 열어 실제 속성명을 확인한 뒤 필터를 맞추세요. Token 속성이 문자열이면 toLong()으로 감싸 합계를 구합니다.
